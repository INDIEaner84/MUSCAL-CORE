# MAS-0100: Storage API — Checkpoint v1.5

## 1. Motivation

MAS-0010 definiert das Gesamtsystem, aber keine konkrete Storage-Abstraktion. MAS-0100 friert den Storage Layer als Checkpoint v1.5 ein: API-first, Backend-austauschbar, ACID oder deklarierte Abweichung, Snapshot + Versioning verpflichtend, Checksum + Integrity Gate verpflichtend.

## 3. Architektur-Invarianten (verbindlich ab Checkpoint)

### I1 — Storage Isolation
Alle Persistenz geht ausschließlich über MAS-0100 API.

### I2 — Determinism Constraint
Jeder MAS-Run muss reproduzierbar sein bei identischem Seed + Input.

### I3 — Capability Enforcement
Kein Node darf externe Effekte ohne deklarierte Capability ausführen.

### I4 — Graph-first Execution
Alle Berechnungen werden als Graph interpretiert, nicht als Sequenz.

### I5 — Trace Obligation
Jede Execution erzeugt vollständigen Trace für MREIL.

## 4. Storage API (frozen)

- Storage API ist abstrakt
- Backend ist austauschbar (SQLite, PostgreSQL, S3)
- ACID oder deklarierte Abweichung verpflichtend
- Snapshot + Versioning verpflichtend
- Checksum + Integrity Gate verpflichtend

## 5. API-Contracts

```
write(collection: str, data: dict) → version_id
read(collection: str, id: str, version?: int) → dict
snapshot() → snapshot_id
restore(snapshot_id) → bool
integrity_check(collection: str) → { valid: bool, checksum: str }
```

## 7. Governance Freeze

Keine Storage-API-Änderungen ohne neuen RFC. Keine Backend-Implementierung ohne bestandene Conformance Tests.

## 8. Fehlerfälle

| Fehler | Ursache | Reaktion |
|--------|---------|----------|
| Write-Fehler | Backend nicht verfügbar | Queue + Retry |
| Integrity-Fehler | Checksum-Mismatch | Snapshot verwerfen |
| Snapshot beschädigt | Speicherkorruption | Letzten validen Snapshot laden |
