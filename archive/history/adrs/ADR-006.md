# ADR-006: Dead Code Deprecation Lifecycle

**Context:** The codebase has 227 Python files, of which 90 are stubs (<20 lines) and many are entirely unimported. Analysis (2026-07-08) identified 6 dead/orphan subsystems:

| Subsystem | Files | Status |
|-----------|-------|--------|
| Distributed | `distributed_*.py`, `core/swarm.py` | Self-contained DAG |
| Swarm | `swarm_*.py`, `event_bus_swarm.py` | Self-contained DAG |
| Vision | `vision_*.py` | Self-contained DAG |
| Browser Pipeline | `browser_*.py` (partial) | Partially used by vision |
| Consensus | `consensus_engine.py`, `emergent_consensus.py`, `weighted_consensus.py` | Self-contained DAG |
| Self-Improvement | `recursive_self_improver.py`, `self_critique.py`, `self_*.py` | Self-contained DAG |
| Meta-Compiler | `meta_compiler.py`, `meta_reasoning_kernel.py`, `compiler_*.py` | Mostly kernel_core-only |
| MCXF Tools | `mcxf_fusion.py`, `mcxf_sql.py`, `mcxf_compression.py`, `mcxf_graph_builder.py`, `mcxf_memory_store.py` | Partially active (fusion used in main_boot) |
| Minimal variants | `minimal_*.py` (8 files) | kernel_core-only |

Without a formal lifecycle, dead code accumulates indefinitely — contributors cannot tell what is safe to delete, tests cannot be trusted to cover the right surface, and security audits waste time on unreachable paths.

**Decision:** We adopt a 4-stage deprecation lifecycle for all dead code:

```
STAGE 1 — Labelled (⚠️ DEPRECATED header)
STAGE 2 — Frozen (30 days, no changes accepted)
STAGE 3 — Archived (moved to attic/)
STAGE 4 — Deleted (after next release)
```

**Rules:**

1. **Labelling:** Any file with zero imports from the active pipeline (`MuscalKernel/MuscalOS/runtime/`) receives a deprecation header. This is done immediately.

2. **Freeze Period:** 30 calendar days after labelling. During freeze, only documentation changes are allowed. Bug reports are logged but not fixed.

3. **Archival:** After freeze, files are moved to `attic/<subsystem>/`. A manifest `attic/INDEX.md` records original path, purpose, and archival date.

4. **Deletion:** After the next tagged release with no regression, `attic/` contents are deleted. The release notes document the removal.

**Exceptions:**
- Files with partial active usage (e.g., `mcxf_fusion.py` used in `main_boot.py`) are NOT candidates for archival unless the active usage is also removed.
- `minimal_graph_memory.py` (pure re-export) is exempt from archival — it can be removed immediately once all imports are redirected.

**Consequences:**
- + Systematic, predictable dead code removal
- + 30-day safety window catches regressions
- + `attic/` provides a safety net without polluting the active codebase
- + Reduces codebase by an estimated 60-70 files within 2 releases
- - Requires discipline to maintain the lifecycle
- - Some files may have undocumented active usage (risk mitigated by freeze)

**Rationale:** Without a formal policy, dead code persists indefinitely. The 4-stage model balances safety (freeze catches unknown dependencies) with progress (predictable cleanup). The `attic/` pattern is proven in large codebase migrations.
