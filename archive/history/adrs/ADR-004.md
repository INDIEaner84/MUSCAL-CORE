# ADR-004: GraphMemory Interface Consolidation

**Context:** Das System hat mehrere Memory-Implementierungen nebeneinander:
`GraphMemory` (`graph_memory.py`, 27 Zeilen), `minimal_graph_memory.py`
(bereits reiner Re-Export), `MCXFMemory` (`minimal_mcxf_memory.py`, 9 Zeilen),
`MCXFMemoryStore` (`mcxf_memory_store.py`), sowie `memory.py` (SQLite, 139 Zeilen).
Es gibt keinen gemeinsamen Vertrag — jede Implementierung hat eigene Methodensignaturen.
Das erschwert Austauschbarkeit, Testbarkeit und Plugin-Integration.

**Decision:** Wir führen ein `MemoryProvider` Protocol in `interfaces.py` ein.
Alle Memory-Implementierungen implementieren dieses Protocol.
Das Ziel ist: Austauschbare Speicher-Adapter hinter einer einheitlichen Schnittstelle.

**Consequences:**
- + EINHEITLICHES Interface für alle Memory-Provider
- + Plugins können eigene Memory-Adapter implementieren (`features/`)
- + GraphMemory, MCXFMemory und memory.py teilen denselben Vertrag
- - Bestehende Code-Stellen müssen aktualisiert werden (minimaler Aufwand)
- - Protocol muss stabil bleiben (Änderungen = Breaking Change)

**Rationale:** Ohne Interface-Protocol sind Memory-Implementierungen
austauschbar. Jeder neue Speicher-Typ müsste manuell in jeden Consumer
eingebunden werden. Mit Protocol wird `memory` zum Dependency Injection
Container — der Kernel fragt `MemoryProvider`, nicht `GraphMemory`.
