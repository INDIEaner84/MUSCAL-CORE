## Architektur-Entscheidungen (relevant für Folge-AI)

### 1. EventStore Auth ist deferred
EventStore hat keine Authentifizierung. Das ist ACCEPTED BY DESIGN für die
aktuelle In-Process-Architektur. Authentication wird in einer späteren
Security-Hardening-Phase eingeführt (erfordert Multi-Process-Architektur).

### 2. Claim/Evidence Boundary ist entfernt
`EventIdentity`, `ProvenanceTag`, `enrich_with_claim_boundary` wurden entfernt,
da sie nie in Produktionspfade eingebunden waren. A-001 (False Agent Claim)
bleibt ein architektonisches Scope-Boundary — keine Code-Enforcement vorhanden.

### 3. Verification braucht jetzt Evidence
`set_verification("verified")` ohne `evidence_receipt_id` wirft `ValidationError`.
`store_verification()` validiert dass `receipt_id` nicht leer ist und
`execution_id` existiert.

### 4. Verification Conflicts werden erkannt
Widersprüchliche Verifications (verified vs failed) für dieselbe `execution_id`
werfen `VerificationConflictError`. Der Check und Insert sind atomar
(selbe `self._lock`-kritische Sektion).

### 5. Replay ist strukturell unterscheidbar
`is_replayed` Spalte in `stored_events` (BOOLEAN NOT NULL DEFAULT 0).
Backward-kompatibel: alter `_replayed` Payload-Marker wird weiter erkannt.
