## 2. Execution Integrity Contract

**File:** `spec/EXECUTION_INTEGRITY_CONTRACT.md`

Defines 10 distinct concepts with explicit trust boundaries:

| Concept | Trust Level | Authority |
|---------|-------------|-----------|
| Intent | UNTRUSTED | Agent (LLM) |
| Claim | UNTRUSTED | Agent (LLM) |
| Authorization | TRUSTED | Governance + SafetyGate |
| Execution Request | TRUSTED | MEL/CU/Pipeline |
| Execution Result | TRUSTED | Executor function |
| Execution Receipt | TAMPER-EVIDENT | UTR (canonical) |
| Verification Request | TRUSTED | VerifierCU/Policy |
| Verification Result | CANONICAL | Verifier function |
| Ground Truth | AUTHORITATIVE | Filesystem/external |

**Hard rules:**
- Never set `VERIFIED` without calling `UTR.verify()`
- Never convert `INCONCLUSIVE` to `VERIFIED`
- Never accept agent claims as evidence
- `INCONCLUSIVE` MUST NOT be promoted to `VERIFIED`

## 3. Receipt Architecture

### Tamper-Evident Hash
```
sha256(receipt_id + tool_name + json(args) + json(result_data) + 
       str(success) + execution_time + execution_id + correlation_id)
```

- Hash computed once during `finalize()`
- Any mutation of sealed fields invalidates the hash
- `verify_integrity()` recomputes and compares
- `TAMPERED` status assigned when hash mismatch detected

### Canonical Receipt Generation
- Receipts are created ONLY by `UTR._build_receipt()`
- Receipts carry `execution_id` (unique per execution attempt) and `correlation_id` (shared across multi-step)
- `finalize()` is called before the receipt is stored in `_receipt_store`

### Serialisation Protection
- `from_dict()` correctly restores `receipt_id` (not generating a new one)
- Verification result is restored from serialized `VerificationResult` object

## 4. Verification Architecture

### Canonical VerificationResult
```python
VerificationResult:
  verification_id: str (uuid)
  execution_id: str
  receipt_id: str
  verifier_id: str
  status: VerificationStatus
  expected_state: dict
  observed_state: dict
  state_diff: dict
  evidence: dict
  verified_at: float
```

### Status values
| Status | Meaning | Can promote to VERIFIED? |
|--------|---------|-------------------------|
| VERIFIED | Expected state matches observed | N/A |
| FAILED | Mismatch detected | No |
| INCONCLUSIVE | Cannot determine | **MUST NOT** |
| NOT_SUPPORTED | No verifier registered | No |
| TAMPERED | Receipt integrity violated | No |

### Verification Flow
1. Integrity check: receipt finalized? hash valid?
2. Verifier lookup by tool name
3. Verifier executes (compiled Python, trusted)
4. Result mapped to VerificationStatus
5. VerificationResult stored in `_verification_store`
6. `INCONCLUSIVE` never promoted to `VERIFIED` (assertion enforced)

## 5. Idempotency & Replay Protection

- `UTR.execute()` accepts optional `execution_id` parameter
- `_execution_store` tracks seen `execution_id` values
- Duplicate `execution_id` returns `ToolResult` with `DUPLICATE_EXECUTION_ID` error
- `metadata["dedup"] = True` flag on duplicate results
- Without `execution_id`, duplicate tool + args execute independently (known limitation)

## 9. Known Limitations

1. **muscal_loop.py is a parallel execution universe** — contains its own EXECUTORS, BrowserAgent, and execute_tool() with NO UTR, SafetyGate, or Governance. Fully functional for standalone loop operation. Deferred to MUSCAL v2.0.

2. **kernel.run() hot path bypasses GovernanceStage** — `run()` at kernel.py:622 calls stages manually and does not invoke GovernanceStage, RoutingStage, or CognitiveUnitStage. Only `_run_pipeline()` includes full governance enforcement.

3. **Verifier independence gap** — The `filesystem.write` verifier compares file content against agent-provided expected content. A truly independent verifier would need access to a separate specification of what content should have been written. Current verifiers are self-consistency checks.

4. **No execution_id → no idempotency** — Without providing `execution_id`, the same (tool, args) pair executes independently each time. Idempotency requires explicit `execution_id` at call site.

5. **Plugin hooks have unchecked ctx access** — `run_hooks()` passes the full context dictionary to plugin callbacks. Any plugin can potentially modify execution results.

6. **Receipt store is in-memory** — `_receipt_store` and `_verification_store` are Python dicts. Receipts are lost on process restart. No persistence layer.

7. **TOOL_REGISTRY fallback in mel.py** — Latent backdoor that activates when UTR returns "Unknown tool." Currently all TOOL_REGISTRY tools are also in UTR, but adding a tool only to TOOL_REGISTRY creates an unguarded path.
