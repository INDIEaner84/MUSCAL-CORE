# E3.4 — Self-Reconstructable Execution Architecture

## Overview

E3.4 enables read-only causal execution reconstruction from persistent and
runtime provenance data. Given an `execution_id`, the system can reconstruct
the available causal history and explicitly classify each relationship as
**VERIFIED**, **INFERRED**, **MISSING**, or **CONFLICT**.

The central architectural invariant:

```
PROVENANCE INTEGRITY ≠ SEMANTIC TRUTH
```

A provenance chain can be internally consistent while its originating decision
or premise may still be wrong. The reconstruction engine preserves this
distinction.

## Data Sources

| Source | Data | Authority | Persistence |
|--------|------|-----------|-------------|
| `UTR._execution_store` | execution_id → ExecutionReceipt | Runtime | In-memory |
| `UTR._receipt_store` | receipt_id → ExecutionReceipt | Runtime | In-memory |
| `UTR._verification_store` | verification_id → VerificationResult | Runtime | In-memory |
| `UTR._expected_state_store` | execution_id → expected_state dict | Runtime | In-memory |
| `decisions` DB table | decision records with trace_id, span_id | SQLite | Persistent |
| GraphState | nodes, edges, types | Runtime | In-memory |
| EventBus `_history` | EventMessage list | Runtime | In-memory |

## Provenance Resolver

```
resolve_execution(execution_id)
    ↓
1. Locate execution in UTR stores
2. Resolve receipt, verify integrity hash
3. Resolve decision from decisions table
4. Resolve trace context from decisions table
5. Resolve verification results
6. Resolve causal graph (in-memory)
7. Classify every relationship
8. Return ReconstructionReport
```

## Identity Model

```
execution_id ──→ receipt_id ──→ integrity_hash (SHA-256)
     │                                │
     ├── trace_id ──→ decisions[].trace_id
     ├── span_id
     └── decision_id ──→ decisions[].id
```

## Evidence Classification

| Status | Definition | Examples |
|--------|------------|----------|
| VERIFIED | Direct authoritative evidence, integrity-validated | receipt in store + hash valid; decision in DB |
| INFERRED | Derived from temporal/correlation evidence | trace_id same across receipt and decision |
| MISSING | No evidence found in any source | execution_id not in any store |
| CONFLICT | Multiple sources disagree | receipt decision_id ≠ decisions table |

### Precedence

```
CONFLICT > VERIFIED > INFERRED > MISSING
```

Any conflict overrides all other classifications.

## Edge Types

| Type | Description | Evidence Source |
|------|-------------|----------------|
| CAUSES | Direct causal relationship | ExecutionReceipt fields |
| AUTHORIZES | Governance authorizes execution | decision_id on receipt → decisions table |
| CONTAINS | Containment relationship | trace_id groups multiple spans |
| CORRELATES_WITH | Temporal/correlation relationship | Same trace_id across records |
| PRECEDES | Temporal ordering | timestamps |
| RETRIES | Retry relationship | same trace_id, new execution_id |
| VERIFIES | Verification result | verification_id → receipt_id |
| PRODUCES | Tool produces result | execution_id → result_data |
| DERIVES_FROM | Derivation | GraphState DERIVES_FROM edges |

## Reconstruction Report

```
ReconstructionReport
├── identity: execution_id, trace_id, span_id, decision_id
├── actors: task_id, agent_id, model_id (if available)
├── governance: policy, decision, authority source
├── execution: state, events, receipt
├── effects: known artifacts, state changes, missing effects
├── verification: verification_id, result, evidence
├── causal_graph: nodes, edges, evidence_status per edge
└── completeness: VERIFIED: N, INFERRED: N, MISSING: N, CONFLICT: N
```

## Provenance Integrity ≠ Semantic Truth

Every reconstruction report separates:

```
provenance_integrity: VERIFIED (the chain is internally consistent)
semantic_truth: NOT ESTABLISHED (correctness of claims is separate)
```

This is not an error. It is a correct epistemic boundary.

## Adversarial Resistance

The resolver detects:
- forged trace_id (no matching trace context)
- forged span_id (no matching span)
- forged decision_id (no matching decision record)
- mismatched execution_id (receipt hash mismatch)
- cross-trace binding (same execution_id in two traces)
- cross-task binding (same decision_id for different tasks)
- orphaned execution/receipt/decision/verification
- stale provenance (timestamp anomalies)
- replayed provenance (duplicate ID with different data)
- receipt vs decision mismatch
- execution vs trace mismatch
- verification vs receipt mismatch
- contradictory timestamps
- duplicate decision identity
- reconstructed from partial data (some relationships MISSING)

## Read-Only Architecture

E3.4 MUST NOT:
- modify decisions
- modify policies
- modify governance outcomes
- automatically correct provenance
- automatically repair historical records
- mutate execution history
- introduce autonomous self-modification
- silently infer missing facts as truth
