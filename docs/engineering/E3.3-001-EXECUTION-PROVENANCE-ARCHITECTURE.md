# E3.3 — EXECUTION PROVENANCE & DECISION TRACEABILITY

## 1. Executive Summary

E3.3 assesses whether MUSCAL can reconstruct the causal chain of an execution.
The current architecture has strong identity for **runtime execution** (execution_id,
receipt_id, verification_id, event_id, session_id) but lacks identity for
**orchestration-level** elements (trace_id, span_id, decision_id, tool_call_id,
artifact_id).

Missing elements are: trace_id, span_id, decision_id, tool_call_id, artifact_id,
request_id, edge_id. High risk: trace_id/span_id (no distributed tracing).

**Recommendation:** Do NOT implement a full E3.3 architecture now. The minimum
viable provenance architecture is:
1. Add `trace_id` as a single correlation ID for each kernel.run() invocation
2. Add `span_id` to ExecutionReceipt for hierarchical causality
3. Add `decision_id` to VerificationResult for governance decision binding
4. Wire existing `decisions` DB table into the kernel pipeline

This achieves meaningful causal reconstruction without creating unnecessary
infrastructure complexity.

## 3. Existing Provenance Mechanisms

### 3.1 Runtime Provenance (COMPLETE)
- **UnifiedToolRuntime** generates execution_id, receipt_id, verification_id
- Receipts have SHA-256 integrity hash, finalized flag
- Dedup via _execution_store prevents replay
- ReceiptStore (in-memory) + FileReceiptStore (JSON) provide persistence

### 3.2 Event Provenance (COMPLETE)
- **EventBus** generates event_id for every message
- **EventStore** persists events to SQLite with cursor-based replay
- **ReplayService** can replay event sequences

### 3.3 Graph Provenance (COMPLETE)
- **GraphState** tracks nodes (node_id, type, timestamp) and edges
- Trace path methods (trace_dependencies, trace_execution_path)
- Debugger adds DebugNode/DebugEdge

### 3.4 Governance Provenance (COMPLETE)
- **Governance** tracks per-agent iteration, token, cost usage
- Violation logging with agent_id, timestamps
- HITL action logging

### 3.5 Agent Provenance (COMPLETE)
- **ProcessManager** spawns/shutdowns agents with lifecycle tracking
- agent_id logged for spawn, crash, heartbeat events

## 4. Gap Analysis

### 4.1 Missing: Distributed Trace Context (trace_id, span_id)
- No trace_id correlates events across a single end-to-end request
- No span_id establishes parent-child execution hierarchy
- No OpenTelemetry integration exists (ADR-009 defers it)
- Risk: HIGH — cannot reconstruct causal chain across kernel.run() boundaries

### 4.2 Missing: Decision Identity (decision_id)
- `decisions` DB table exists but is never written to from kernel pipeline
- No decision_id in execution flow
- Risk: HIGH — governance decisions cannot be linked to execution receipts

### 4.3 Missing: Tool Call Identity (tool_call_id)
- Tool calls identified by execution_id/receipt_id only
- No tool_call_id to link plan steps → tool execution
- Risk: MEDIUM — ExecutionReceipt already captures tool_name + execution_id

### 4.4 Missing: Artifact Identity (artifact_id)
- No artifact_id for filesystem.write outputs
- Risk: MEDIUM — artifact identity is implicit (file path)

### 4.5 Missing: Request Identity (request_id)
- No request_id for external API calls
- Risk: MEDIUM — session_id partially fills this role

### 4.6 Partial: Orchestration-Level Identity (intent_id, plan_id, step_id)
- These exist as in-memory variables in kernel.run() but are not persisted
- Cannot reconstruct: intent → plan → step → tool_call → receipt chain
- Risk: MEDIUM

## 5. Threat Model

| Threat | Vector | Detection | Mitigation |
|--------|--------|-----------|------------|
| Forged decision_id | Agent injects fake decision in context | verification_id mismatch | Add decision_id to execution chain |
| Agent forgery | Agent claims false agent_id | Governance agent_id mismatch | trace_id binding to agent_id |
| Model forgery | Agent claims false model_id | No detection today | Add model_id to ExecutionReceipt |
| Tool call forgery | Agent fabricates tool call | execution_id dedup | Weak — needs tool_call_id |
| execution_id collision | Random UUID collision | Dedup detection | Existing (extremely low probability) |
| Receipt replay | Replay old receipt with new execution | SHA-256 hash mismatch | Existing |
| Cross-task contamination | Leak IDs between parallel tasks | No detection today | trace_id isolation |
| Retry corruption | Second attempt overwrites first state | execution_id dedup | Existing |
| Delegation provenance loss | Sub-agent loses parent context | No detection today | trace_id propagation |
| Provenance truncation | Truncate long execution chains | No detection today | span_id nesting |

## 6. Provenance Graph Proposal

**Recommendation: Hybrid model (Event-sourced causal graph)**

```
Intent_ID ──→ Plan_ID ──→ Step_ID ──→ ToolCall_ID ──→ Execution_ID ──→ Receipt_ID ──→ Verification_ID
    │            │           │             │                │                │                │
    └──────┬─────┘           │             │                │                │                │
           │                 └──────┬──────┘                │                │                │
           │                        │                       │                │                │
    trace_id ───────────────────────┴───────────────────────┴────────────────┴────────────────┘
    span_id (hierarchical: span.parent_span_id)
```

Rationale:
- **trace_id** — single correlation ID per kernel.run() invocation
- **span_id** — hierarchical nesting for sub-operations
- **Linear chain** — captures the common case (intent→tool→verification)
- **Graph edges** — EventStore + GraphState provide branching for parallel execution
- **No DAG required** — GraphState already provides causality inference

## 8. Causal Relationships

```
trace_id
   ├── intent_id (derived at MKC stage)
   │   └── plan_id (derived at Bridge stage)
   │       └── step_id (per plan step)
   │           └── tool_call_id (per tool invocation)
   │               └── span_id (UTR execute)
   │                   ├── execution_id (dedup key)
   │                   ├── receipt_id (persisted)
   │                   ├── decision_id (governance check)
   │                   └── verification_id (verifier call)
   └── session_id (from config)
       └── event_id (EventBus)
```

## 9. Persistence Model

**No new database tables required.** All new provenance fields fit into
existing storage:

- ExecutionReceipt: add `trace_id`, `span_id`, `decision_id` fields
- VerificationResult: add `decision_id` field
- ReceiptStore: automatically persists new fields via to_dict()
- EventStore events: already include session_id; can include trace_id

---

## 10. Integrity Model

- `trace_id` and `span_id` are integrity-hashed via ExecutionReceipt.finalize()
- No separate cryptographic signing required for provenance metadata
- Receipt integrity chain (SHA-256) protects all provenance bindings

---

## 11. Parallel Execution Model

Multiple trace_ids can be correlated via correlation_id (existing mechanism).

```
correlation_id = "shared-scenario"
  ├── trace_id = "A" (execution_id = "A-1", "A-2")
  └── trace_id = "B" (execution_id = "B-1")
```

---

## 12. Retry Model

Retries use a new execution_id (dedup prevents same execution_id reuse).
trace_id is shared across retry attempts.
span_id differentiates original vs retry.

---

## 13. Delegation Model

Sub-agents inherit the parent trace_id.
Sub-agents generate their own span_id with parent_span_id set.
This enables causal chain reconstruction through delegation.
Current ProcessManager/Governance already tracks agent_id.

---

## 14. Artifact Lineage

No artifact_id is proposed. Artifacts are identified by:
- file path (for filesystem.write)
- execution_id + receipt_id (for any tool output)
Correlation via trace_id is sufficient for artifact lineage.

---

## 15. Verification Lineage

Existing chain:
```
execution_id → receipt_id → verification_id
```

Proposed addition:
```
decision_id → execution_id → receipt_id → verification_id
```

decision_id links governance decisions to execution receipts.

---

## 16. Human-in-the-Loop Provenance

HITL actions are logged by Governance (agent_id, action, timestamp).
The `decisions` DB table can record human approval decisions.
No UI changes required for provenance; the data model already supports it.

## 21. Architecture Decision

> The minimum viable provenance architecture that provides meaningful causal
> reconstruction without creating unnecessary infrastructure complexity is:
>
> **Add 3 provenance fields (trace_id, span_id, decision_id) to existing
> identity carriers; generate them at the kernel.run() boundary; wire the
> existing `decisions` DB table. Do NOT implement a DAG provenance system.**
>
> This achieves: "For every relevant execution, MUSCAL can reconstruct what
> happened, why it happened, under which authority it happened, what actually
> changed, and how the resulting state was independently verified."
